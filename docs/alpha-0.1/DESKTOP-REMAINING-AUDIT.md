# Desktop baseline and remaining executable scope

Source audit28 October2026. This distinguishes existing behavior from the next implementation; mobile apps are excluded by the owner. Existing native file, inbox and policy acceptance is recorded in their scope reports. Release/platform evidence remains separate from source implementation.

| Surface | Existing executable baseline | Remaining concrete work |
|---|---|---|
| Queues | `daemon/queues.rs`, `queue_schedule.rs` and `queue_tests.rs` already persist queues, membership, held jobs, retries, speed limits, missed windows and time-zone/overnight rules. `backend/live.ts` calls native queue list/put/control/delete/configure, and maps server-held jobs. | `QueueKind` supports Download only; synchronization queues and metered-network policy are absent. Do not rebuild the scheduler. Native footer previously claimed limits/schedules were unapplied; corrected to describe the real native engine while preserving hosted/scripted descriptions. Desktop finishing actions still require the app process. |

Continuous push delivery, atomic snapshots spanning pages, larger-list pagination and final installed virtualization/accessibility acceptance remain separate work. |
| Workflow runtime | `zeus-workflow/runtime.rs` and daemon `workflows.rs` already implement bounded public-page plans, pagination, detail extraction, naming/routing, dedupe, durable frontier/job intents, reports, drift pause and control. The native Site grabber is a separate cancellable public crawler. | No dedicated native Runs page or closed desktop plan/dry-run/run/control/manifest routes. `/api/v1/runs` reads at most2 pages and currently turns list failures into an empty result. | Interoperability | Parent owns the new MCP HTTP/App resource work and tests; extension baseline currently passes its full suite/builds. | Installed browser/trust-channel acceptance and final host interoperability remain evidence gates. Recommended next work after the current acceptance batch:

1. Add a shared handle-relative filesystem capability and convert local file/index/archive consumers. Keep root identity, quarantine, current scopes, atomic no-replace output and write-ahead receipts; close path resolution races rather than layering more path checks. Send the core-file design before touching shared code.
2. Complete acceptance for the bounded native durable history path, then evaluate continuous progress subscriptions and consistent paged job snapshots. The implemented history is descriptive and cannot overwrite current job state; it opens no extra daemon listener.
3. Build a native Runs view over existing workflow APIs, including errors, saved exact plans, reports, pause/resume/cancel and manifest actions. Approval remains on a verified terminal; authenticated rendering and continuation need their own contracts rather than a fake frontend switch.
4. Add the deterministic organizer/artifact desktop review path only with an explicit capability design. Follow with metadata-only, budgeted model classification that yields a reviewed rule proposal.
5. Design queue synchronization and metered-network behavior independently of the already-working scheduler. Review frontend settings that remain marked planned before presenting those capabilities as implemented.

This audit does not promote source-only or planned capabilities to accepted alpha features. The phase roadmap still contains hardening, fault matrices, installed-platform and signing/registration inputs that require their own evidence.
