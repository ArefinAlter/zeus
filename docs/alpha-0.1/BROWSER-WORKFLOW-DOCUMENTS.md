# Reviewed browser workflow documents

This is a post-alpha implementation on `feature/workflow-browser-pages`. It is absent from the published `v0.1.0-alpha.1` binaries. It implements the plain-document part of W01. It does not claim rendered pages, scroll, item sinks, revised-plan continuation, multi-origin sessions or full W01–W03 completion.

The desktop Runs view offers an explicit browser session mode; the CLI uses `workflow plan --browser-origin <https-origin>`, and `zeus_workflow` accepts `request.browser_origin`. Both native peers negotiate `session.page`. Public workflows retain native pinned HTTP networking. There is no automatic fallback between the two modes.

The first browser planning request needs a human site grant already displayed by the extension, browser host access and one connected attested profile. Before any sampling it returns a separate browser-network approval and a plan ID. Its review binds the owner, origin, grant, profile, exact URL digest, 32 total preview reads, 512 KiB per document, 25-second browser request deadlines and a 15-minute review lifetime. Failed reads consume their reserved preview allowance. Retry with the returned plan ID and a fresh retry key after the human review.

The normalized plan contains `session.document_mode = "browser_origin"` and the reviewed `session.profile_id`. These are included in the plan hash and workflow approval facts. A separate workflow approval creates the grant for that exact run. The verified interactive CLI/TUI path remains available. The extension accepts its resulting consent only if it previously displayed that approval and still has host permission. Unpacked extension identities cannot decide approvals. A second connected profile cannot substitute, including for the workflow's file-session leases.

The daemon checks exact HTTPS origin, public DNS, allowed domains, robots and pacing immediately before dispatch. The browser resolves and connects under its own policy; the native peer-pinning guarantee is unavailable. Redirects, IP literals, local hostnames and private-context fallback are refused. This residual DNS-rebinding boundary is stated in the review and [ADR 0019](../adr/0019-browser-workflow-documents.md). No browser profile, cookie store or credential file is read for document acquisition.

Automated evidence is recorded separately from installed-browser acceptance:

- Extension: 330 tests across 23 files, strict lint, typecheck and production build pass. The new cases cover exact subject/profile/grant, displayed and undisplayed terminal consent, missing host permission, expiry/revocation, private context, redirects, binary/oversized bodies, deadline and correlated cancellation. No cookie API is called for document acquisition.
- Desktop frontend: 59 tests and both harness/desktop builds pass.
- Native broker fixtures use authenticated in-memory relays and real durable journal grants. They verify exact response identity, workflow/site separation, review/grant revocation, task cancellation, terminal grants and a second connected profile. Plan tests bind the exact profile and plan hash and preserve the shared preview budget across reopen. The complete daemon run passed 216 cases; two new fixture setup errors were corrected and their focused suites passed (18 browser-related tests and one exact session-policy test). No production behavior was changed to make those fixtures pass.

Installed-browser acceptance remains pending: a person must install/connect the extension, grant host permission, display the approval there, decide the exact network/plan reviews through a verified trust surface, and exercise an authorized HTTPS site. The automated fixtures do not establish that a real site accepts the account. A store identity or signing credential is not assumed.

Final Windows gates: session unit/conformance 37 + 5; workflow 62; API/IPC 90 + 8; MCP 50; CLI trust 8; daemon/CLI/MCP strict Clippy clean. The CLI verifies the browser review hash and explicitly shows the unavailable peer-pinning guarantee and absence of any new session grant. Spec validation covers 261 documents; the 15-tool catalogue is 39,551 bytes with digest `4fc2e1da9976c3c55ea07bca7c57c8c2c6a93674e2f0fa37ee17700efc6e5b91`. The native code was tested on Windows; no installed Linux-browser acceptance is claimed.
