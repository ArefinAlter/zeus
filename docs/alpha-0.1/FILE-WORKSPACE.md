# Desktop file workspace, alpha0.1

This implementation is independent Rust code plus voidtools' public MIT SDK2. Proprietary IDM/Everything decompilation is not included. Android/iOS applications are outside this release's owner-approved scope.

## Executable surfaces

| Surface | Behavior and bounds |
|---|---|
| Native indexed search | Parsed Everything-style query groups run in Rust; one page contains at most500 rows, generation-bound paging refuses changes between pages, and retention is O(offset+page), not O(all matches). Exact counts/logical-size totals cover the current scoped index. Root inclusion/exclusion changes revoke cached rows synchronously. A small trigram Bloom mask skips impossible text matches before exact comparison; regexes use Rust's bounded linear-time engine. Native `host:` provenance queries and regex lookaround/backreferences return explicit unsupported errors. |
| Index lifecycle | Scope enumeration starts with a persisted snapshot, then reconciles. Directory watchers have a1,024-message queue and16,384 pending-path cap; dropped/coalesced/overflowed notifications trigger reconciliation. Failed enumeration retains prior rows rather than pretending their files disappeared. Snapshot-save failures and unavailable/replaced roots remain visible in the UI. Search caps at500,000 entries and16 configured roots. |
| Live folders | Existing direct-disk500-row browsing includes files excluded from the search index. Keyboard/virtualized rows preserve selected path identity across refresh. Search-only folders remain read-only. |
| Two-pane manager | Files → Two-pane manager opens independent scoped folder paths, cursors, selection and virtualized keyboard navigation. Each pane retains at most10,000 loaded entries. Wide windows show both; narrow or short windows switch Left/Right without resetting either folder. Stale navigation results cannot replace the new folder, and changing read scopes immediately hides old rows. Copy/Move preset the other pane's destination in the existing review dialog; source management rights and quarantine remain enforced by Rust. F5/F6 open those reviews; F2/Delete open rename/delete reviews. |
| Folder comparison | A complete, error-free listing in both panes enables current-directory name/type/size/date comparison. Missing pages or skipped entries disable comparison. Matching metadata is explicitly distinct from equal content; subfolders are not recursively compared. Selecting a regular file on each side can invoke bounded SHA-256 verification through the native duplicate-verification route. This view never automatically replaces or deletes an item. |
| File operations | Existing cancellable recursive copies preflight at most100,000 entries/128 levels, preserve sources, reject links/junctions and never replace targets. The live native rename/move/undo/copy/mkdir routes now use retained core directory capabilities, separate read/write root sets and opened-object identities. Durable write-ahead receipts, guarded identity-based undo and explicit interrupted-receipt reconciliation cover files and folders. Root replacement, quarantine, changed objects, occupied original paths and revoked management roots refuse undo. Cross-drive moves require Copy followed by a separate reviewed deletion; directory creation is explicit. |
| Storage inspection | Top50 logical folder/type totals, and up to100 equal-size candidate groups. Equal size is not verified duplication. Explicit content verification hashes2–32 regular files and at most1GiB, rechecks metadata/scopes, respects quarantine and leaves files untouched. Logical sizes do not claim allocated disk bytes or hard-link-deduplicated physical usage. |
| ZIP create/extract | Native Rust ZIP manifests are previewed and saved before execution. At most2 workers,32 retained receipts,10,000 expanded entries including implicit directories,4GiB of source/expanded content,1GiB ZIP input and ten-minute execution bounds. Stored/Deflate ZIPs only; unsafe/reserved/ADS/traversal paths, case collisions, file-parent conflicts, links/special files, encryption, split/SFX/ZIP64 containers and excessive expansion ratios are refused. Source data is unchanged; a private staging object is published with atomic no-replace rename after CRC/length checks. SHA-256 labels distinguish ZIP bytes from extracted-file manifests. |
| Archive recovery | Cancellation is checked during I/O and before publication. Staging paths/identities and a publication digest are retained durably. A crash around publication never causes automatic replay. Explicit reconciliation requires the same file identity and matching output digest before reporting completion. Archive reads, staging, publication and reconciliation use held directory/file capabilities. New previews bind the destination-parent identity. Cleanup preflights the bounded link-free staging tree before deleting expected identities inside current writable roots. Uncertain/foreign/changed outputs remain for human review. |
| Optional Everything | Storage and history → Everything uses a pinned source-built read-only SDK2 broker, explicit instance (`1.5a` or default), configured read scopes, literal name queries and501-row raw windows. Parent-side scope/exclusion/link/current-metadata filtering precedes display. Offsets are labeled live, not stable snapshots. The source-built broker has no ES/Everything INI/profile/index-file loading, no GUI/history/rebuild controls and no new service or daemon listener. It is stopped/joined after ten seconds. Missing/changed helpers, absent instances and incompatible output fail explicitly. Zeus's own index stays functional. |

The optional broker is **not an independent NTFS/MFT/USN implementation**. Everything must be running and indexing the requested folder. The installed1391a build also predates newer Everything Index Journal APIs. Source, license and repeatable build instructions are in `tools/everything-broker/`; distribute `LICENSE-SDK.txt` with the Windows executable. Enabling a reviewed helper is a native person's settings action; agents receive no new approval or file-scope authority.

## Authority and containment

Read roots come from included folders. Write roots come from engine download folders and explicit Manage files settings. The root's file identity is pinned at enable/startup and checked again; a replaced root is not silently accepted. Native operations check fresh complete quarantine facts and never decide daemon approvals. Helper executable bytes/file identity are pinned separately from file scopes. The optional provider cannot expand reads or writes and root revocation is checked again after an IPC query.

Native move/rename/undo retain source and parent handles across the durable intent. File/folder copies resolve and open each component relative to retained roots, reject intermediate/final links and preserve no-overwrite creation. Background copies compare source identities and metadata against preflight, then recheck opened files after copying. Managed-root acquisition compares the opened root with its enablement identity. Windows handles prevent directory replacement while in use; failed copies delete the opened output object. Unix capabilities follow the directory object if another process renames it; source rename and cleanup identity checks are not atomic compare-and-act syscalls against a hostile same-user process.

Engine default I/O, index scans/direct folder listings/optional Everything result filtering, external file-manager launch and delete/trash still use the existing canonical/identity/path checks. They retain a final path-use race and must be converted before claiming complete filesystem hardening. Legacy direct-library rename/move helpers are not the converted desktop receipt routes. Power-loss durability and weak/removable/network filesystems still require the planned fault matrix; directory watchers are not assumed lossless.

The native UI follows status metadata and requested result pages; it does not serialize or duplicate the complete index into the webview. Existing wire paths/timestamps for index rows remain compatible; daemon API work uses its typed contract separately.

## Archive directory-capability checkpoint

ZIP preview, source-tree traversal, extraction, publication, digest reconciliation and staging cleanup now use the shared held-directory implementation. ZIP inspection and decompression reuse opened source files; exclusive staging creation and atomic no-replace publication preserve existing outputs. Destination-parent identities are captured at preview and rechecked at execution and recovery. Ready plans from older receipts require a fresh preview; their recorded outputs remain inspectable and identity-checked cleanup/reconciliation stays available.

Cleanup walks the entire bounded staging tree before deletion, rejects links/special files, then removes opened expected identities from children to root. Replaced staging or changed published bytes stay unresolved. ZIP validation now also rejects implicit parent case conflicts such as `A/first` plus `a/second`, and previews share the filesystem's device-alias rules. Cancellation is rechecked at the publication boundary. A definite no-replace collision is a failed publication with retained staging, while ambiguous publication errors remain uncertain.

The shared core additions are retained-directory metadata/sync, advisory no-follow entry presence, portable filename validation and expected-object removal. `Filesystem`/`DataFile` remain unchanged for the engine and Ogun. Private archive receipt reads and atomic writes still use the existing application state writer; this conversion does not claim to replace that boundary. Windows directory sync is explicitly not a power-loss guarantee. Unix compare/unlink and compare/rename retain the documented same-user race limits.

## Retained preview and duplicate reads

Native preview and duplicate-verification routes now acquire read capabilities from the settings service's existing root identities. Each regular file stays open with its parent chain; bytes are never read by reopening the displayed ambient path. Metadata and identity are rechecked before returning output. Images and optional line counting enforce the4 MiB limit during reads, even if the source grew after metadata capture; text output remains limited to64 KiB. SVG remains source text. Unreadable/changed/link targets produce a refused preview rather than partial content.

Duplicate verification retains all selected handles until the final recheck, so a detected change to an earlier file invalidates the complete result. Multiple names/hard links of one object count once. The2–32 selection and1 GiB limits remain, with a cooperative two-minute deadline between blocking reads. There is no deletion or atomic filesystem snapshot, and a same-user writer that preserves metadata is outside this consistency guarantee. Current quarantine and read-scope rules still apply.
