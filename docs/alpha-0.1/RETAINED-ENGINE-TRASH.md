# Retained engine data and reviewed trash follow-up

This is an isolated follow-up to the Windows alpha checkpoint. The published alpha assets still use core `a944e43035e9de9f5871ec6afd10c036e13457ad`. Do not describe this work as shipped until its integration and replacement binary acceptance are recorded.

The engine default now acquires `RetainedFs` from the configured write roots and their admitted identities. Injected `Filesystem` implementations and `RealFs` remain available. Each data file retains its opened parent chain. Verification hashes that same opened object, compares its before/after identity, length and modification time, writes native provenance through the retained object/parent, flushes it, and publishes it without replacing an existing destination. Cancel and orphan cleanup require the expected object identity. Finalization recovery opens and checks the journaled identity before publication. Existing scope checks, job records, grants, quarantine decisions and commit order remain.

Windows provenance uses the fixed `Zone.Identifier` stream relative to the retained parent. The original file remains open without delete sharing, and the opened stream identity is compared before truncation. Unix attributes use the opened file descriptor. The platform FFI stays in `zeus-fs::sys`. A capability authorizes an opened object; this is not an operating-system sandbox against another process running as the same user. Unix no-replace rename/unlink still has its documented compare-versus-entry-replacement interval.

`zeus-fs::Trash` retains its root and resolves day folders, payloads and bounded immutable receipts through directory handles. New receipts bind the payload and original parent identities. Cross-volume copies are flushed and published without replacement before removing the expected source; a separate immutable copy receipt records the new payload identity before publication. Legacy records remain visible, but records lacking identity cannot authorize restore or purge and must be preserved for manual recovery. The additive `receipt_state` inspector reports `legacy_manual_recovery`; the organizer refuses an automated undo plan with an explicit recovery error. There is no automatic migration or adoption of missing identities. Any later legacy adoption requires a separately reviewed design. A regression loads the exact older flattened JSON shape and proves listing survives restart while restore, occupied-path overwrite and purge leave both payload and receipt untouched. Purge is an explicit library operation, never scheduled by this change. The public `move_to_platform_trash` compatibility helper retains its existing path-based semantics.

The daemon organizer retains its approved root and parent directories through execution. Its write-ahead audit, current consent and human approvals still decide admission; filesystem capabilities provide containment after admission.

Native file-manager trash now uses `.zeus/trash/<random-id>/<original-name>` inside the selected managed root. It is a same-volume, no-replace move using the existing durable move receipt, so files and folders can be restored with **Undo / restore** in **Storage and history** after restart. The UI explicitly calls it **Zeus trash**. Current managed roots, quarantine, identity/metadata and occupied-path checks also apply to restore. `.zeus` is excluded from ordinary indexing even if optional exclusion patterns are cleared. Receipts show recorded logical file bytes; folder contents are not silently counted as a directory metadata size. Trash continues consuming disk space. Automatic expiry/purge is not enabled; permanent deletion remains an explicit reviewed action.

Native permanent deletion fully preflights each selected tree before removing anything. It refuses links/reparse points and special entries, retains parent capabilities, bounds the walk to 20,000 entries, 128 levels and two minutes, and removes expected objects deepest first. Newly inserted children prevent nonempty-directory removal; a failed operation returns the paths which still need review. Native history reconciliation reads both locations through the current retained root identities and never replays a move.

Private application receipt persistence continues using the existing atomic state writer. External file-manager launch and the public platform-trash compatibility helper remain separate ambient interfaces; no claim is made that every application path consumer has been converted.

Validation receipts are maintained in `D:/verne-build/retained-consumers/evidence`. Final test counts, platform execution and review commits are added after the gates complete. Actual Unix execution, cross-volume dispatch on a second Windows volume, adversarial same-user writes that preserve metadata, and power-loss behavior require their own evidence; helper-level copy/cleanup tests alone do not establish those results.

Windows API references: [NtCreateFile relative opens](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile) and [FILE_FS_FULL_SIZE_INFORMATION layout](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_fs_full_size_information).
