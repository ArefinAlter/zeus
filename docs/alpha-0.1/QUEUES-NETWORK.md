# Native synchronization queues and network-cost policy

A native queue can use `kind: "sync"` and `sync_every_hours` (1–720, default 24). The desktop exposes **Queue behavior → Watch for new versions** for named queues. Completed members remain watched, and an existing completed download can be assigned to a synchronization queue. Start and Stop control both its download scheduler and its checks; an explicit Start makes completed watches due immediately.

The daemon keeps watched job IDs, pending replacement IDs, last result and next check in `queues.json`. Each serialized scheduler tick probes at most one due file, with a ten-second deadline. Checks run only while their queue is running and neither the kill switch nor the metered-network policy blocks them. A stopped queue does not probe. Failed checks wait for the configured interval rather than retrying in a tight loop.

Checks use the shared engine's transport and consent rules. A strong ETag identifies the representation; a strong Last-Modified date requires a known length. Missing/weak identity, quarantined files, caller-pinned size/hash, or custom request headers produce an explicit unverifiable result. Session requirements and check failures have separate results. Neither a changed URL nor an unchecked size alone proves a new version.

A changed representation creates a new engine job using the original caller identity and final destination directory, the original basename as its filename hint, and rename-only collision handling. The original file and its bytes remain intact. Stable representation-bound idempotency makes crash retries safe. The new job retains the ordinary engine grants, approvals, quarantine and integrity checks. Current requester permissions, service destination roots and signed team restrictions are rechecked before background effects. Revoking the original requester blocks later versions. A failed replacement leaves the completed baseline watched; a completed replacement becomes the next baseline. Queue status reports the actual outcome, including its pending job ID.

The durable queue defaults also accept `network_mode` (`auto`, `metered`, `unmetered`) and `pause_on_metered` (default true). The desktop Connection page stores these settings in the daemon. Automatic detection queries Windows' active Internet connection cost or active NetworkManager interfaces on Linux, at most every 30 seconds with a five-second deadline. Metered, roaming and data-limit conditions hold engine-managed downloads and synchronization probes. Unavailable detection is reported as **unknown**. If an existing metered hold loses its cost observation, it stays held until a known unmetered result or an explicit policy change.

The policy records only jobs it paused. Pre-existing manual pauses remain paused, and an explicit pause clears automatic ownership even when the job was already paused. A global kill switch clears that ownership so changing networks cannot undo a global stop. This applies to engine-managed downloads; it does not intercept arbitrary device traffic or claim to pause other applications or independently running upload providers. Verifying/finalizing files finish safely rather than being interrupted.

Validation: 27 native queue and real-engine tests passed, including changed bytes saved beside the original, requester revocation, stop during a probe, restart durability, unknown network cost, manual pauses and the global stop. Four focused queue API tests and the full 59-test frontend suite passed; TypeScript and the production build passed. Combined daemon strict validation is recorded with the coordinated release gates. No live provider, operating-system setting change, or device-wide network interception is claimed.
