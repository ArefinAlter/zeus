# Durable intake packages

The desktop Inbox collects HTTP(S) source requests into daemon-owned packages before a reviewed enqueue. Metadata editing, exact deduplication, package pagination, destination/collision preview, dispatch receipts and explicit pending-batch reconciliation use ten typed `inbox.*` daemon methods. No additional listener, approval decision or file-root grant is added. Android/iOS apps are outside the alpha scope.

Ownership comes only from the authenticated credential ID. Public list/get/preview/receipt views contain redacted resource addresses and bounded daemon facts (explicit `include_history=true` enables at most16 saved previews/768KiB and the newest20 dispatch projections/256KiB in package.get; history is empty by default and each entry page is also capped at256KiB); the original `NewJob`, header/referrer/hint fields and dispatch keys stay in the private redb package record. A human-capable credential may explicitly supply `owner_credential_id` to the three read methods to inspect another credential's redacted packages, retained review facts and dispatches. Agent/service credentials, including the desktop GUI credential, are refused that selector. Explicit history exceeding its byte ceiling returns `api.payload_too_large` with guidance to inspect an individual dispatch; it never silently drops rows to fit. Cross-owner mutation and dispatch are never accepted. The desktop's existing restricted `app` credential owns its intake, while external agents own theirs.

A package edit requires its current revision. An addition accepts1–200 requests and at most512KiB; identical typed records (including their request metadata and untrusted label) are retained once within a package. Query-value changes remain distinct requests. Every mutation key is bound to the full typed payload and owner; reusing a key with different input fails. Removing intake metadata never cancels or deletes downloads; archive/unarchive preserves receipts.

Review selects at most50 pending entries and resolves concrete safe filenames and destinations through the existing enqueue dry-run, using the current caller and write-root checks. Explicit filename hints are sanitized; missing names use the last URL path segment, or `download.bin`. The preview refuses occupied destinations, duplicate destination paths in its batch and unreadable collision checks. It does not probe remote HTTP content or promise a future server-provided filename. Session-dependent requests remain separately approval-gated. Reviews expire after ten minutes; beginning a new review creates a new immutable handle.

Submit persists its exact hidden enqueue request and a stable inner `jobs.enqueue` key before dispatch. It forces no-replace output behavior, so a file created after review cannot be silently overwritten or renamed. The existing engine revalidates execution scope and approval facts. A pending dispatch fences package edits, survives daemon restart, and can only retry the same retained request/key. Per-entry enqueue receipts recover the original accepted job IDs if the process stops after enqueue but before saving the inbox result. Completed responses are immutable; retries do not mint a replacement batch. The inbox does not automatically replay pending requests on startup.

Bounds are explicit:10,000 entries and16MiB private serialized state per package;256 packages per owner;16 current preview handles and2,000 retained dispatches per package;20,000 mutation receipts per owner;65,536 rows per table and256MiB of total logical serialized state, with32MiB reserved against new rows. Capacity errors preserve existing recovery state. Logical bounds do not claim a physical redb disk-size ceiling: copy-on-write/free pages and filesystem allocation require separate platform measurements. There is no receipt garbage collector or destructive package-delete API in this alpha.

The new desktop Inbox is separate from Link grabber/Media grabber. It provides package creation/editing, one-address-per-line intake, selected/next50 review, destination and approval facts, start, paginated entries, metadata removal, archive and pending-batch reconciliation. Typed APIs also accept request metadata and filenames beyond the simple desktop intake form. Browser interception and media intake retain their existing review paths.
