# 0016: Directory capabilities for local file operations

Status: additive primitive and native copy/move/undo/mkdir, archive data paths, previews and duplicate verification converted; engine and deletion consumers remain to be converted. Private application receipt persistence remains a separate boundary.
Owner direction: complete the desktop file manager and the non-mobile 0.1 roadmap.

Path canonicalization and identity rechecks do not protect the interval before a later path-based open, rename or delete. Introduce an additive directory-capability implementation in `zeus-fs`. It retains open root and parent directories and resolves only normal child components. A final symlink, junction or reparse point is refused. Opening a configured root is the explicit ambient-authority boundary; subsequent operations are relative to held handles. Read roots and managed write roots remain distinct.

Use the maintained `cap-std`/`cap-fs-ext` primitives for bounded directory-relative resolution. Preserve exclusive creation and atomic no-replace publication; ordinary rename-with-replacement is not an acceptable substitute. The Windows no-replace primitive uses `NtSetInformationFile(FileRenameInformation)` with an opened source and destination directory handle; Unix uses directory-relative rename with NOREPLACE. Platform FFI stays in the isolated system module. File identities come from the opened objects. Operations keep their parent capabilities alive until completion.

Retain the existing `Filesystem`/`DataFile` contracts and `RealFs` entry point for compatibility. The additive `DirectoryCap`/`RenameSource` types serve opted-in consumers; injected simulation filesystems remain usable. Convert the engine's default file access and the native file/index/archive operations incrementally, with each converted surface recorded in the file-workspace report. Do not claim all path races closed while an ambient-path consumer remains.

A capability authorizes the directory object that was opened. On Unix an independently renamed directory can retain that authority through its open descriptor; this is not an OS sandbox against another process running as the same user. Windows directory handles must retain the sharing restrictions required by the capability library. Existing scope, quarantine, file-identity, approval, collision and durable-receipt checks remain required in addition to path containment.

Acceptance covers component traversal/ADS/device-name rejection, intermediate and final links, rename collisions, held-directory identity during replacement, partial outputs and failure cleanup. Windows execution, Rust 1.90 Windows/Linux-target compilation and Ogun compatibility are recorded in FILE-WORKSPACE.md; actual Linux execution remains pending. Unsupported atomic platform operations fail explicitly. Existing release downloads are unchanged until release acceptance.

References: [cap-std directory capabilities](https://docs.rs/cap-std/4.0.3/cap_std/fs/struct.Dir.html), [no-follow directory/file options](https://docs.rs/cap-fs-ext/4.0.3/cap_fs_ext/), and [Windows relative rename information](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information).

The Win32 `SetFileInformationByHandle` wrapper rejected a non-null relative directory handle with error87 on the acceptance machine. The isolated Windows module therefore uses the documented NT rename information class directly with synchronous handles and no replace flag. Incomplete copy cleanup deletes the opened Windows output object; Unix checks its identity before directory-relative unlink. Unix lacks atomic rename/unlink conditioned on a file identity, and power-loss durability on each target filesystem still needs the planned fault matrix.

Archive conversion: retain read/destination/staging directory capabilities throughout preview, execution, publication and reconciliation. New plans bind the destination-parent identity at preview; legacy receipts remain inspectable/cleanable but require a fresh preview before starting. ZIP validation, decompression, CRC/length verification and hashing reuse opened files. Cleanup preflights a bounded, link-free staging tree and removes expected opened identities in postorder, then the empty root; it must not call an ambient recursive-delete helper. Core additions are retained-directory metadata/sync, no-follow entry presence and expected-object removal. Windows removes the opened object; Unix retains its documented compare/unlink race against same-user entry replacement. Private receipt persistence continues through the application's existing atomic state writer and is documented separately from archive data-path containment.


Read-consumer conversion: native previews and duplicate verification acquire existing read-root identities and retain parent/file handles throughout the request. Preview image and line-count reads are limited while reading, not only by earlier metadata, and never reopen a checked ambient path. Duplicate hashing retains every selected file through a final identity/metadata recheck, deduplicates hard-link aliases by file identity, and keeps the existing 32-selection/1 GiB bounds with a cooperative two-minute I/O-loop deadline. These checks do not provide an atomic snapshot or prevent a same-user writer from modifying bytes while preserving metadata. Index scans, direct folder listings, the optional Everything result filter and external file-manager launch paths are still separate consumers.

Index/listing conversion: add streaming directory-name enumeration and OS metadata from an opened no-follow child to the existing capability. The index scanner, watcher refresh, direct paged listings and Everything row validation must use retained roots; unknown read errors retain prior rows, while a confirmed absent child can remove its cached subtree. Preserve native hidden/system filtering and bounded page memory. Helper executable staging and private index snapshot persistence remain explicit application-state boundaries.

Follow-up decision: the native file manager uses Zeus-owned, same-root `.zeus/trash` with an explicit UI label and the existing durable Undo receipt. The platform recycle APIs accept ambient paths and cannot preserve the retained-object boundary. The compatibility helper remains unchanged. Normal indexing excludes managed internal trash, storage/history reports recorded logical file sizes without claiming folder totals, and no automatic expiry/purge runs. Engine default data access, opened-object verification/provenance/publication, expected-object cleanup and application-trash restoration are converted in a separate review branch; see [retained engine/trash report](../alpha-0.1/RETAINED-ENGINE-TRASH.md) for release and validation status. Native permanent deletion preflights bounded link-free trees, then removes expected identities through retained parents.

Compatibility amendment: older application-trash JSON stays readable and listed with `legacy_manual_recovery`. It cannot authorize automatic restore or purge; no identity is inferred from the current path. Any adoption of legacy entries requires a separate reviewed design. The existing platform-trash compatibility helper is unchanged.
