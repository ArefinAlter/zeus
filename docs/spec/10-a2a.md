# 10 — A2A bridge

Status: Draft 1, 2026-10-16. This is a product contract, not a claim that the bridge is released. Depends on [00](00-conventions.md), [05](05-daemon-api-v1.md), [07](07-approvals-trust-surface-and-consent.md), [08](08-workflow-plan-v0.md), and [ADR 0010](../adr/0010-one-local-listener-http-bridges.md).

## 1. Boundary and interoperability profile

Zeus offers an optional Agent2Agent bridge for other programs to request work and observe tasks. The bridge is a separate process and an ordinary `agent` client of `zeusd`. It never opens the journal or holds browser material. Starting the daemon does not start the bridge.

The target is the A2A 1.0 profile. A2A JSON fields use camelCase; discovery uses `/.well-known/agent-card.json`. These conventions were checked against the [official specification](https://a2a-protocol.org/latest/specification/#55-json-field-naming-convention) and its [discovery section](https://a2a-protocol.org/latest/specification/#82-discovery-mechanisms) on 2026-10-16. The implementation must pin a protocol release and validate fixtures against that release before advertising interoperability; a moving `latest` page is not a version lock. Zeus's internal API continues to use snake_case.

Initially the bridge implements JSON-RPC only. An interface is advertised only when its transport and methods work. Streaming, push callbacks, remote deployment, extended cards, and card signatures are false or omitted until separately implemented and tested. No compatibility alias silently changes an old method's meaning.

## 2. Listener and identity

1. The default endpoint binds only `127.0.0.1`, on a configured port. The daemon itself never binds TCP.
2. A token from a dedicated private file is required on every RPC. Tokens are compared in constant time and never accepted in URLs. Authentication precedes parsing a large body or contacting the daemon.
3. Host must exactly match the configured loopback authority, including port. Origin is absent for non-browser clients or must match an explicit allowlist. Wildcard origins, `null`, unexpected hosts and forwarded-host overrides are refused.
4. Request bodies are bounded to 1 MiB; the connection has an authentication/header deadline, a body deadline, and bounded in-flight requests. Errors do not echo supplied bodies or credentials.
5. A remote bind requires an explicit configuration change and an independently verified mTLS or OAuth deployment profile. Until this profile exists, non-loopback addresses are rejected before bind. Declaring an authentication scheme in the card alone does not implement it.
6. Every peer maps to a stable authenticated identity. Task reads, cancellation and subscriptions are scoped to that identity. An unauthenticated discovery request can receive only the public card; it cannot enumerate local tasks, paths, origins, approvals or clients.

## 3. Work and task mapping

The initial executable skill is `fetch_file`, using the validated `NewJob` shape of 05. `rescue_download` requests a session-aware download; it cannot supply cookies or approve consent. `organize_files` and `convert_files` are advertised only after their planners, approvals and runtime operations are integrated. Unsupported skills return a typed failure before creating work. Natural-language input never executes directly: it requires the bounded planning path of 08 and the same approval as any other plan.

A submission has a stable message identifier and an explicit idempotency key. The bridge binds the peer, skill, normalized payload and key before forwarding. A retry returns the same task; reusing a key with different work is a conflict. The bridge must survive restart without creating duplicate downloads. A context groups tasks; possession of a context or task identifier grants no authority.

| Zeus job state | Task state |
|---|---|
| queued, probing | submitted |
| downloading, retry_scheduled, paused, verifying, finalizing | working |
| awaiting_approval | input required |
| awaiting_session | authentication required |
| completed | completed |
| canceled | canceled |
| failed with policy denial | rejected |
| other failed | failed |

The Rust mapping emits the protocol's `TASK_STATE_*` enum spellings. A paused task carries a clear status reason. Approval-required responses identify the approval and tell the peer that a human must use a Zeus trust surface. Sending another A2A message, an authentication response, a forged approval object or an affirmative sentence cannot satisfy that requirement.

Cancel maps to `jobs.control` cancel and is idempotent for an already canceled task. It does not delete a completed file. Polling maps to current daemon state, never a bridge cache that can outlive the authoritative task. Events resume using durable daemon sequence cursors; progress can be coalesced. Reconnect and lag require a fresh snapshot followed by replay.

## 4. Results and privacy

A completed task returns artifact metadata: an opaque artifact/job identifier, hashes, size, verification state and a sanitized name. It does not inline downloaded bytes, signed source URLs, credentials, session material, approval facts or requester annotations. A local path is disclosed only through an explicitly authorized local profile. Remote cards and tasks never advertise a local `file://` path as a remotely retrievable download.

A quarantined result stays quarantined. A peer cannot open, materialize into an executable location, convert, overwrite or delete it by changing task metadata. Later artifact delivery must use a scoped export capability with expiry and audit, or an independently authenticated byte-delivery service. The initial bridge provides metadata only.

Peer content, remote filenames and titles are untrusted text. They remain visibly separate from daemon-derived status. Tool instructions embedded in content do not alter the method allowlist, budgets, destinations or peer identity.

## 5. Card, errors and acceptance

The public card declares the exact endpoint, implemented protocol version and only enabled skills. It has no user name, local filesystem path, current queue, session origin, credential or private model configuration. Authentication scheme declarations must match the running server. A disabled capability returns the protocol's unsupported-operation error; it is not emulated through a generic daemon-RPC forwarder.

Before enabling the bridge, hermetic tests must cover: independent peers cannot read/cancel each other's tasks; token/Host/Origin rejection before backend calls; duplicate submissions across restart; every job-state mapping; approval escalation remains human-only; secret-marker exclusion; bounded request/response handling; disconnected subscribers release resources; disabled skills are absent from the card. A conformance client must negotiate the pinned protocol release and complete submit → inspect → cancel and submit → completion workflows.

## 6. Versioning and open issues

Protocol changes require new fixtures and an explicit supported-version entry. Zeus's mapping and task metadata carry their own profile version; undocumented fields do not become executable instructions.

Open issues: pin an upstream release/schema artifact and digest; implement the standalone bridge and CLI command; choose the persistent peer/task index; define authenticated artifact byte delivery; validate remote mTLS/OAuth deployments. Until those gates pass, the crate's mapping helpers are available but the product must not claim a runnable A2A service.
